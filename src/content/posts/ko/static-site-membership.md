## 왜 정적 사이트에 회원제가 필요했나

교회 홈페이지는 예배 안내, 소개, 연혁, 사진 앨범이 대부분이라 HTML/CSS/JS 정적 사이트로 충분했습니다. 서버가 없으니 비용도, 관리할 것도 적습니다.

하지만 두 가지는 정적 페이지만으로 안 됐습니다.

1. **교인 전용 공간**: 가입 → 관리자 승인 → 등급(목사·집사·청년) 부여
2. **앱 테스터 신청서**: ‘성경&찬양’ 앱 비공개 테스트에 참여할 사람의 Google 계정·이름·연락처를 받기

## 구조: 정적 페이지 + Firebase

- 페이지는 모두 정적 HTML로 GitHub Pages에 둡니다.
- 로그인·가입·마이페이지·관리자 페이지만 **Firebase Auth와 Firestore**를 씁니다.
- `auth-nav.js`가 로그인 상태에 따라 메뉴의 “로그인 ↔ 전용 공간”만 바꿉니다.

이 구조에서 중요한 사실이 하나 있습니다. **Firebase 설정값(API 키 포함)은 웹페이지 소스에 그대로 보입니다.** 웹 앱용 Firebase 키는 비밀이 아니라 “어느 프로젝트인지” 알려주는 식별자이기 때문입니다. 따라서 데이터를 지키는 것은 키를 숨기는 것이 아니라 **Firestore 보안 규칙**입니다.

## 로그인 없는 신청서를 지키는 규칙

테스터 신청서는 로그인하지 않은 사람도 써야 했습니다. “아무나 쓸 수 있는 컬렉션”은 가장 위험한 곳이라 규칙을 꼼꼼히 잡았습니다.

- **생성만 허용**합니다. 읽기·수정·삭제는 관리자만 할 수 있습니다.
- **문서 ID를 소문자 이메일**로 씁니다. 같은 계정으로 다시 쓰면 규칙상 `update`가 되어 거절되므로, 한 계정은 한 번만 신청할 수 있습니다.
- **허용 필드를 제한**합니다. 정해진 필드 외에는 넣을 수 없습니다.
- **형식을 검사**합니다. 이메일·휴대폰은 정규식, 이름은 1~30자, 개인정보 동의는 필수입니다.
- **상태는 `pending`만**, 생성 시각은 **서버 시각만** 허용합니다. 신청자가 스스로 “등록 완료” 상태로 만들 수 없습니다.

규칙의 뼈대는 아래와 같은 모양입니다. (실제 규칙의 필드와 정규식은 사이트 저장소에 있습니다.)

```js
match /testerRequests/{email} {
  allow create: if
    email == request.resource.data.email.lower() &&
    request.resource.data.keys().hasOnly(['email', 'name', 'phone', 'consent', 'status', 'createdAt']) &&
    request.resource.data.consent == true &&
    request.resource.data.status == 'pending' &&
    request.resource.data.createdAt == request.time;
  allow read, update, delete: if isAdmin();
}
```

신청 → 관리자 목록에 표시 → 삭제까지 실제로 동작하는 것을 확인했고, 테스트가 끝나면 신청 정보를 지우도록 안내 문구를 넣었습니다.

### 관리자는 어떻게 정하나

“관리자만 관리자를 지정할 수 있다”는 규칙을 쓰면 첫 관리자를 만들 방법이 없습니다. 첫 관리자는 **Firebase 콘솔에서 직접** 지정하고(부트스트랩), 이후로는 규칙에 따라 기존 관리자만 새 관리자를 지정할 수 있게 했습니다.

## 개인정보와 공개 범위

이 사이트에는 실제 성도 사진이 약 1,225장 있습니다. 기술적으로 잘 만드는 것보다 **누구에게 보이는가**가 더 중요했습니다.

- 사진은 업로드 전에 웹용(~1600px)으로 줄이고 연도·행사별로 정리했습니다.
- 이미지 첨부 게시판은 Firebase Storage(유료 요금제)가 필요해 넣지 않았습니다. 기능을 줄이는 것도 개인정보를 덜 다루는 방법입니다.
- 사이트 공개 범위는 계속 다시 검토하고 있고, 코드는 포트폴리오에도 공개하지 않습니다.

## 배운 점

- 정적 사이트에도 **회원제를 “가볍게”** 붙일 수 있습니다. 대신 서버 코드가 없으니 **보안 규칙이 곧 백엔드**입니다.
- 로그인 없이 쓰는 컬렉션은 생성만, 필드는 화이트리스트로, 값은 형식 검사로 좁혀야 합니다.
- 웹용 Firebase API 키는 숨길 수 없고, 숨길 필요도 없습니다. 지켜야 하는 것은 규칙입니다.
